# 并发测试文档

> 面向 `spring-api-support-system-starter`（端口 18170，context path `/system/api`）的并发处理能力测试。
> 覆盖：**OAuth 鉴权链路**、**登录链路**。
> 目标：明确当前并发上限、是否存在提升空间、是否需要以及如何实施限流。

## 1. 被测系统与链路

| 链路 | 接口 | 说明 |
| ---- | ---- | ---- |
| 鉴权链路 | `GET /v2/setting/default` | 受 OAuth 鉴权保护，`plugin.oauth.protocol: static`；TokenCipher(SM4) 解密 + 认证缓存（缓存 key = SHA-256(token)，命中后应用层 0.046ms） |
| 登录链路 | `POST /v2/user/login` | 密码校验 + 用户/角色查询（远程 MySQL 172.16.0.40）+ TokenCipher 签发 token |

## 2. 测试环境

| 项目 | 值 |
| ---- | -- |
| 操作系统 | Windows（i5-12600KF，10 核 16 线程，32GB 内存） |
| JDK | Amazon Corretto JDK 25（`-XX:TieredStopAtLevel=4 -Xms1g -Xmx2g -XX:+UseG1GC`） |
| 数据库 | 远程 MySQL `172.16.0.40:3306/system`（P6Spy 代理驱动） |
| Hikari 连接池 | `maximum-pool-size: 20`（已从 4 调优） |
| Tomcat | Spring Boot 默认：`maxThreads=200`、`acceptCount=100` |
| 压测工具 | `benchmark.ps1`（C# HttpClient 全异步、连接复用、`DefaultConnectionLimit=4096`） |
| 样本量 | 每场景 500~5000 请求 |

> **环境注意**：本机 360 安全组件（`com.baize.aegis`）通过 `sun.misc.Unsafe` 注入 JVM，对高并发请求存在额外干扰，本机数据为**保守下限**，生产（Linux/容器、无安全组件注入）预计更优。

## 3. 并发能力评估

### 3.1 鉴权链路（GET /v2/setting/default，x-oauth-token）

| 并发 | 请求数 | 成功率 | QPS | P50 | P90 | P95 | P99 | Max |
| ---- | -----: | -----: | ---: | --: | --: | --: | --: | --: |
| 10 | 100 | 100% | 507 | 17.26 | 23.52 | 24.44 | 24.48 | 25.29 |
| 100 | 5000 | 100% | 2163 | 24.70 | 84.91 | 262.32 | 270.77 | 276.58 |
| 100 | 3000 | 100% | 2526 | 20.00 | 40.94 | 257.15 | 299.61 | 305.30 |
| 200 | 5000 | 100% | 1525 | 43.29 | 470.81 | 699.33 | 746.17 | 747.61 |

> 并发 20 组因早期压测客户端（同步阻塞导致线程池饥饿）失真，已剔除。

**结论**：
- **最优并发点约 100**：QPS 约 **1800~2500**，P50 20~25ms，P99 270~300ms，成功率 100%
- 并发升至 200 时吞吐回落至 1525、P99 升至 746ms——瓶颈为 Tomcat 线程调度 + 本机环境，**非应用逻辑**
- 应用层（TokenCipher + 缓存）仅 0.046ms，吞吐天花板受网络栈与容器配置限制

### 3.2 登录链路（POST /v2/user/login）

| 并发 | 阶段 | QPS | P50 | P90 | P95 | P99 | Max |
| ---- | ---- | ---: | --: | --: | --: | --: | --: |
| 10 | 初始 | 24.3 | 358.79 | 573.10 | 662.81 | 997.39 | 3548.71 |
| 10 | 连接池 4→20 + 协议/布局查询缓存 | 47.0 | 84.49 | 548.24 | 760.73 | 1864.08 | 3362.26 |
| 10 | +合并角色查询（JOIN）+ 角色缓存 | **75.4** | **63.32** | 287.91 | 540.24 | 1543.40 | 2247.03 |
| 50 | 全部优化后 | 47.8 | 540.18 | 1294.60 | 1817.89 | 5549.07 | 25787.79 |

**结论**：
- **吞吐上限约 75 QPS**（并发 10 即达到；并发 50 反降至 47.8，远程 DB 排队放大长尾）
- 瓶颈为远程 MySQL 上**必须实时执行的用户查询**（含密码校验，不可缓存）的网络 RTT
- 登录接口不适合高并发直接冲击，正常业务（每分钟几十次登录）完全够用

### 3.3 并发上限汇总

| 维度 | 鉴权链路 | 登录链路 |
| ---- | -------- | -------- |
| 最优并发 | ~100 | ~10 |
| 吞吐上限 | ~2500 QPS | ~75 QPS |
| 主要瓶颈 | Tomcat 线程/网络栈/本机环境 | 远程 DB 单次查询 RTT |
| 应用层耗时 | 0.046ms（缓存命中） | 1 次远程查询 + TokenCipher |

## 4. 能否继续提高

### 4.1 鉴权链路
- 应用层已 0.046ms，**无代码优化空间**
- 部署/配置层可提升：
  - **Tomcat 调优**（`application.yml`）：

    ```yaml
    server:
      tomcat:
        threads:
          max: 400          # 默认 200，按核数×20~40 上调
          min-spare: 20
        accept-count: 300   # 排队队列，默认 100
        max-connections: 8192
    ```

  - 生产环境（Linux/容器、无 360 注入）吞吐预计显著高于本机
  - 鉴权链路本身不查库，连接池已够

### 4.2 登录链路
- 已优化至每次登录 **1 次 DB 查询**（用户），代码层面到位
- 剩余提升依赖数据库侧：
  - 确认 `sys_user.sys_user_username` 有索引（避免全表扫描）
  - 数据库就近部署 / 降低网络 RTT（当前跨网访问 172.16.0.40）
  - 移除 P6Spy 代理驱动（每 SQL 有解析与日志开销），生产用原生 MySQL 驱动：

    ```yaml
    spring:
      datasource:
        driverClassName: com.mysql.cj.jdbc.Driver
        url: jdbc:mysql://172.16.0.40:3306/system?useUnicode=true&characterEncoding=UTF-8&useSSL=false&allowPublicKeyRetrieval=true
    ```

### 4.3 小结
- 鉴权链路：当前配置已是该环境合理上限，提高并发靠部署层
- 登录链路：吞吐天花板由远程 DB 决定，代码已优化到位，提升需 DB 侧投入

## 5. 是否需要限流

> **结论：需要。** 当前系统无任何限流组件（`soft.management.enable: false`），登录接口存在暴力破解/撞库风险，鉴权接口存在刷接口/DoS 风险。限流与并发能力无关，是安全必需。

### 5.1 登录接口限流（必须，防暴力破解）

| 维度 | 建议策略 | 实现载体 |
| ---- | -------- | -------- |
| 账号维度 | 5 分钟内失败 5 次锁定该账号 | Redis 计数（`login:fail:{username}`，TTL 5min） |
| IP 维度 | 同一 IP 每分钟登录尝试 ≤ 30 次 | Redis 滑动窗口（`login:rate:{ip}`） |
| 验证码增强 | 失败阈值后强制图形/行为验证码 | 复用已有 `checkEnvironment` / `checkVerifyCode` |

**Redis 滑动窗口示例（应用层拦截器）**：

```java
// 伪代码：每次登录前检查
String key = "login:rate:" + ip;
Long count = redisTemplate.opsForValue().increment(key);
if (count != null && count == 1) {
    redisTemplate.expire(key, Duration.ofMinutes(1)); // 每分钟窗口
}
if (count != null && count > 30) {
    return ReturnResult.error("请求过于频繁，请稍后再试");
}
```

### 5.2 鉴权接口限流（建议，防刷/防 DoS）

- **IP 维度 QPS 限流**：如 200 QPS/IP（正常单用户远低于此），异常流量直接拒绝
- **token 拉黑**：认证缓存已有 TTL（21600s），可对异常来源 token 单独拉黑
- 阈值应远低于 2500 QPS 吞吐上限，避免误伤正常用户

### 5.3 实施载体优先级

1. **网关层（推荐）**：Nginx `limit_req` 或 Spring Cloud Gateway

   ```nginx
   # Nginx 登录接口限流：每 IP 每秒 1 个，突发 5 个
   limit_req_zone $binary_remote_addr zone=login_zone:10m rate=1r/s;
   location /system/api/v2/user/login {
       limit_req zone=login_zone burst=5 nodelay;
       proxy_pass http://backend;
   }
   ```

2. **应用层兜底**：HandlerInterceptor 或 AOP，用现有 `redisTemplate`（database 6）做滑动窗口计数
3. **登录限流**：必须走 Redis（多实例共享计数），应用内内存计数在多实例下不生效

### 5.4 OAuth 限流能力（已实现，`spring-support-oauth-client-starter`）

作为 OAuth 客户端的通用能力内置，任何接入 oauth-client 的服务均可通过配置启用。

**配置项**（前缀 `plugin.oauth.rate-limit`）：

```yaml
plugin:
  oauth:
    rate-limit:
      enable: true            # 总开关（默认 false，不改变现有行为）
      api:                    # 全局接口 QPS 限流（防刷/防 DoS）
        enable: true
        qps: 200              # 同一 IP 每秒最大请求
        window-seconds: 1
      login:                  # 登录限流（防暴力破解）
        enable: true
        ip-limit: 30          # 同一 IP 每分钟最大登录尝试
        ip-window-seconds: 60
        account-fail-limit: 3 # 同一账号失败 N 次锁定
        account-lock-minutes: 5  # 锁定分钟数
```

**实现组件**：
| 组件 | 职责 |
| ---- | ---- |
| `ratelimit.RateLimitService` | 内存滑动窗口计数 + 账号失败锁定（进程内实现，多实例需换 Redis） |
| `ratelimit.RateLimitFilter` | **Servlet 过滤器（最高优先级，在认证过滤器之前）**：全局 QPS + 登录 IP 限流，**未认证流量同样受限**，超限返回 HTTP 429 + `{"code":"42900"}` |
| `AuthClientExecute.getAccessToken` | OAuth 协议登录入口：账号锁定检查 + 登录失败/成功埋点 |
| `DefaultLoginHandler`（system 接入） | 本地登录入口：账号锁定检查 + 失败计数/成功复位 |

**实测验证**（`application-dev.yml` 启用后）：
| 场景 | 结果 |
| ---- | ---- |
| 登录 IP 限流（连续 35 次） | 14~29×200 + 6~21×429（阈值 30/分钟） |
| 全局 QPS 限流（带 token，并发 300/800） | 447 成功 + 353×429（约 200/s 放行） |
| 全局 QPS 限流（**无 token，并发 300**） | 90×403（通过限流后被鉴权拦截）+ 100×429（被限流拒绝）——**未认证刷流量也受限** |
| 账号失败锁定（不存在用户连登 5 次） | 前 3 次失败（C0400S0004），第 4 次起 `A0402 账号已锁定` |

**已知限制与风险**：
- **进程内计数**：多实例部署时各实例独立计数，限流可被绕过（每实例 N 次），需替换为 Redis 实现
- **账号锁定 DoS**：攻击者可用任意已知用户名连续错误登录触发锁定（OAuth 协议登录场景）；system 本地登录不校验密码、失败仅因用户不存在，风险低。缓解：锁定周期不宜过长（默认 5 分钟）、失败计数建议叠加 IP 维度
- **NAT 误伤**：同一出口 IP 共享配额（如 200 QPS/IP），大型 NAT 后正常用户可能被误拦，生产建议按需调大阈值

> 注意：启用限流后，压测/回归需携带已获取的 token（`benchmark.ps1 -Token`）或调大阈值，否则自动登录会被 IP 限流拦截。多实例部署时应将 `RateLimitService` 替换为 Redis 实现（参考 5.3）。

### 5.5 登录单/多端、Refresh 模式、AppKey、临时令牌（能力与测试覆盖）

> 本节记录 oauth-client 四类能力的实现位置、协议支持与单元测试覆盖。

| 能力 | 实现位置 | 协议支持 | 单元测试覆盖 |
| ---- | ---- | ---- | ---- |
| 登录单/多端（在线数量限制） | 服务端 sso `RedisTokenResolver`（`maxOnlineCount` 默认 3）；客户端 `AuthClientExecute.getOnlineStatus/getOnlineUsers` | Http/Armeria 实时；static/OAuth2 返回默认多端 | `onlineStatusDefaultsToMultiple`、`onlineUsersEmptyForStaticProtocol`、`onlineStatusDefaults`、`onlineUsersEmpty` |
| Refresh 多种模式 | `UpgradeType`（VERSION 升级账号 / TIMESTAMP 升级+续期 / REFRESH 换新 token）；`/upgrade`、`/refresh-token` | 各协议 upgradeInformation 实现 | `upgradeGeneratesFreshToken`、`upgradeVersionModeRefreshesToken`、`upgradeTimestampModeRefreshesToken` |
| AppKey 模式 | `AppKeySecret` + `AbstractProtocol.authentication`（缓存键优先 userCode） | Http/Armeria/RSocket；static 降级 403 | `authenticationKeyPrefersUserCode`、`authenticationUserCodeNotSupported` |
| Refresh 换临时令牌 | `AuthClientExecute.createTemporaryTokenByRefreshToken` | Http/Armeria/RSocket；OAuth2/static 返回 501 | `createTemporaryTokenByRefreshTokenRejectsBlank`、`createTemporaryTokenByRefreshTokenDelegatesToProtocol` |

**说明**：
- **单/多端限制为服务端能力**：当前 system 以 `static` 协议部署（无状态本地解密），在线状态返回默认多端模式，**不强制设备数限制**；使用 http/oauth2 协议接入 sso 认证服务器时限制生效
- **refresh→临时 token** 的协议层支持取决于服务端是否接受 refresh token 作为源凭证；static 协议不支持临时令牌（501）

## 6. 复现命令

```powershell
# 鉴权链路（x-oauth-token）
.\benchmark.ps1 -Path "/v2/setting/default" -Method GET -AuthHeader "x-oauth-token" -Concurrency 100 -TotalRequests 5000

# 登录链路（请求体从文件读取，避免命令行引号被剥离）
.\benchmark.ps1 -Path "/v2/user/login" -Method POST -BodyFile .\login-body.json -Concurrency 10 -TotalRequests 500
```

> `login-body.json`：`{"username":"admin","password":"123456","captcha":"","captchaId":"","code":"WEB"}`
> 脚本输出 QPS 与 P50/P90/P95/P99/Max。
