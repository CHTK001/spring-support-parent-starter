### 加密与签名能力汇总

| 协议 | 是否加密传输请求体 | 是否携带 x-sign 签名 | 说明 |
| ---- | ------------------ | -------------------- | ---- |
| static | 否（令牌本身用 SM4 加密） | 否 | 本地解析，无网络请求 |
| http / http-lite | 是（`enableEncryption=true` 时 createData AES，`x-oauth-encode` 头标记） | 是（`SignUtils.generateSignFromMap` MD5） | 请求头 `x-oauth-sign`、`x-oauth-serial`、`x-oauth-uuid`、`x-oauth-timestamp` |
| armeria | 是（同上） | 是（同上） | 与 HTTP 协议同一加密/签名实现 |
| oauth2 | 否（form-urlencoded + Basic Auth） | 否 | 遵循 OAuth 2.0 标准（内省/令牌端点） |
| rsocket | 是（同上） | 是（元数据 metadata 携带） | 与 HTTP 协议同一加密/签名实现 |

## 四、测试过程中发现的问题与改进

| # | 问题 | 影响 | 处理 |
| - | ---- | ---- | ---- |
| 1 | `AesCodec.generateIv` 使用 SHA-256 的 32 字节摘要作为 IV，而 AES/CBC 要求 IV 必须为 16 字节，导致 `Codec.build("aes", ...)` 加解密失败 | 依赖 createData 加密的 http / armeria / rsocket 协议在 `enableEncryption=true` 时不可用（system 使用 static 协议，未受影响） | `AesCodec.java`：IV 取 SHA-256 摘要前 16 字节 |
| 2 | 认证缓存写入时使用 `Value.of(...)` 包装，读取时直接强转为 `AuthenticationInformation`，类型不一致导致缓存不命中 | 缓存优化未生效，令牌每次请求重复走协议 | `AbstractProtocol.readAuthenticationInformation`：读取时先解包 `Value` 再强转 |
| 3 | 父 POM 默认 `skipTests=true`，测试默认不执行 | 测试无法在默认构建中运行 | 文档化执行方式，不改动全局默认配置 |

> 问题 1、2 已修复并随模块重新编译验证，系统后端鉴权回归通过。
