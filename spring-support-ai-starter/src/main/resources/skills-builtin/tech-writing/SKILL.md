# 技术写作指南

## 一、动笔之前

- 明确读者：给谁看（新人/维护者/外部开发者）、他们已知什么、读完要能做什么。
- 明确文档类型：教程（手把手）、How-to（解决具体问题）、参考（查 API）、解释（讲原理）——不同类型的组织方式完全不同。
- 一句话大纲：这篇文档要回答的核心问题是什么？写不进这句话的内容删掉。

## 二、结构组织

- 倒金字塔：先给结论/快速上手，再展开细节；读者 30 秒内应能判断「这篇是否解决我的问题」。
- 常用骨架：背景与目标 → 前置条件 → 步骤（含可验证结果）→ 常见问题 → 参考链接。
- 每节只讲一个主题；小标题写成「能扫读的问题/动作」而不是「杂项、其他」。
- 步骤编号化，每步有明确动作与预期结果（「执行 X 后，应看到 Y」）。

## 三、表达技巧

- 短句优先，一句话一个意思；主动语态（「服务返回 404」而不是「404 被服务返回」）。
- 术语第一次出现给出定义或链接；同一概念全文用同一个词，别「配置/设置/参数」混着叫。
- 避免「显然」「简单地说」「只需」——对读者不成立的简单会制造挫败感。
- 数字、版本、路径、命令写准确；模糊表述（「很快」「大量」）要么量化要么删除。

## 四、代码示例

- 示例可运行：完整到能复制执行（含 import、依赖版本、启动方式）；省略处用 `...` 明示。
- 展示「正确姿势」而非「能跑就行」：错误处理、资源释放、安全注意点都要在。
- 注释解释「为什么」，代码本身解释「怎么做」；不要逐行翻译代码。
- 示例覆盖典型场景 + 一个边界场景；输出结果一并给出。

## 五、图表与格式

- 流程用图（时序/流程/架构），数据用表；图要有图注与阅读顺序提示。
- Markdown 规范：标题层级不跳级、列表不嵌套过深、代码块标语言、表格给对齐。
- 中英混排：中文与英文/数字之间留空格；专有名词保持官方大小写（MySQL、Kubernetes）。

## 六、维护

- 文档头部写明适用版本与最后更新时间；过期内容标注「已废弃」并给替代链接，而不是悄悄删除。
- 代码评审把文档当作交付物：接口变更必须同步更新文档。
- 留反馈渠道（issue/评论区），定期根据高频问题反哺 FAQ。

## 七、检查清单

- [ ] 读者与文档类型明确
- [ ] 30 秒能判断文档是否解决自己的问题
- [ ] 步骤可执行、结果可验证
- [ ] 示例完整可运行且覆盖边界
- [ ] 版本、更新时间、反馈渠道齐全
