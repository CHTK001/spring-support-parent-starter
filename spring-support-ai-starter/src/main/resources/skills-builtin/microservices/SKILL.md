# 微服务架构指南

## 一、服务拆分

- 按业务能力/限界上下文拆分，不按技术层拆；一个服务一个完整业务（数据+规则+编排）。
- 拆分判据：独立部署价值、团队边界、数据隔离；能合并的单体先合并，避免分布式单体的成本。
- 禁止服务间共享数据库：数据所有权唯一，跨服务读走 API/事件，不穿透别人的表。

## 二、通信

- 同步 HTTP/gRPC：简单直接，注意超时、重试与重试风暴（重试要带退避与预算）。
- 异步事件：解耦与削峰，事件要版本化、可回放；消费方幂等。
- 接口契约先行（OpenAPI/proto），变更保持向后兼容；废弃字段先标记再下线。

## 三、注册发现与配置

- 注册中心（Nacos/Consul/Eureka）只做寻址，业务数据不进注册中心。
- 配置中心管理多环境配置，敏感信息加密；配置变更要有灰度与回滚。
- 服务实例元数据（版本、机房、权重）用于灰度路由与就近调用。

## 四、网关与边界

- 网关统一做认证、限流、路由、协议转换；业务规则不要写进网关。
- 对外 API 版本化（/v1、/v2），废弃版本给出迁移期。
- BFF（面向前端的后端）聚合多服务数据，避免前端串行调用 N 个服务。

## 五、熔断限流降级

- 熔断器保护调用方：连续失败打开熔断，半开探测恢复；避免雪崩式连锁故障。
- 限流在入口（网关/服务）按容量设定：令牌桶/滑动窗口；核心接口与营销接口分开限流。
- 降级预案明确「砍什么」：返回缓存/默认值/简化流程；预案要演练，不能只写在文档里。

## 六、分布式事务

- 优先通过业务设计避免跨服务事务；同一服务内用本地事务。
- 需要最终一致：本地消息表/事务消息 + 对账补偿；TCC/SAGA 用于强一致诉求的少数场景。
- 一切跨服务写操作要有幂等键与对账任务，假设任何一步都可能失败。

## 七、可观测性

- 三支柱：日志（结构化+traceId）、指标（QPS/RT/错误率/资源）、链路追踪（全链路采样）。
- 每个服务暴露健康检查与就绪探针；部署滚动发布 + 快速回滚能力。
- 告警面向症状（错误率/延迟/饱和度），不是面向单台机器 CPU。

## 八、检查清单

- [ ] 服务边界按业务能力划分，无共享库穿透
- [ ] 同步调用有超时/重试预算，异步事件幂等可回放
- [ ] 熔断限流降级策略已配置并演练
- [ ] 跨服务一致性走最终一致 + 对账
- [ ] 日志/指标/链路三件套齐全，能十分钟内定位一次线上问题
