# 消息队列使用指南

## 一、选型

- Kafka：高吞吐日志/事件流、回溯消费；RocketMQ：业务消息、事务消息、延迟消息；RabbitMQ：低延迟路由、灵活拓扑。
- 先明确诉求（吞吐/延迟/顺序/事务/延迟），再选型；不要为用而用——同步调用能解决的不要上 MQ。

## 二、可靠投递

- 生产端确认：Kafka `acks=all` + `retries`；本地消息表/事务消息保证「业务落库与发消息」原子意图。
- 消息要有唯一业务 ID（orderNo 等），不要只有自增 msgId。
- 消息体精简，大字段放引用（存 DB/对象存储，消息里带 ID）；消息版本号便于兼容升级。

## 三、幂等消费

- 默认假设消息会重复（at-least-once）：消费端按唯一业务键判重（DB 唯一索引 / Redis setnx）。
- 「查了再插」有并发窗口，最终靠唯一索引兜底；更新类消费用条件更新（`WHERE status = 'INIT'`）防重复执行。
- 消费失败不吞：可重试错误（依赖暂不可用）走重试队列；不可恢复错误进死信并告警。

## 四、顺序性

- 全局顺序代价高，绝大多数业务只要「同一业务键有序」：Kafka 按 key 分区、RocketMQ 顺序队列。
- 分区内单线程消费；扩容分区/队列会破坏既有顺序，需评估兼容。
- 不要用「先查状态再处理」实现顺序——并发下失效，靠分区路由保证。

## 五、延迟与重试

- 延迟消息（订单超时关闭等）用 RocketMQ 延迟级别或 Kafka 时间轮方案；重试退避要设上限与告警。
- 重试消息与首投消息区分 topic/队列，避免阻塞正常消费。
- 大量积压：先扩消费者实例（在分区数内），再评估加分区/降级非核心消费。

## 六、监控与治理

- 核心指标：生产/消费 TPS、消费滞后（lag）、重试量、死信量、broker 磁盘水位。
- 消费者要做优雅停机（提交位点/确认后再退出）；重启不丢消息、不重复确认。
- 消息链路接入 traceId，串联生产→消费全链路日志。

## 七、检查清单

- [ ] 消息有唯一业务 ID 与版本
- [ ] 生产端确认机制开启，关键链路用事务消息/本地消息表
- [ ] 消费端幂等，重试与死信分流并告警
- [ ] 顺序消费按业务键路由，不依赖查状态
- [ ] lag/死信/磁盘水位有监控
