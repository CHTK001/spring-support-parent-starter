正确的不变量**不是**「共享单例从不重建」，而是「重建必须发生在**无身份线程**」：

```

  11:09:48.009 [cat-handler-126]  [SysAiUserSetting] 用户 ops 覆盖已写入
  11:09:48.010 [cat-handler-126]  [Face] 人脸设置变更（用户级）…        ← 同一请求线程，事件由用户写入发出
  11:09:48.025 [cat-handler-126]  [Face] 账号 'ops' 人脸检测模型未配置   ← 按 ops 自己的配置
  11:09:48.070 [cat-handler-126]  [Face] 账号 'admin' 人脸库就绪 3/3 条  ← admin 未被波及
  11:09:48.077 [onPool-worker-6]  [FaceClientManager] 开始热重建          ← **无身份异步线程**（读全局，不污染）
  11:09:48.100 [onPool-worker-6]  [Face] 人脸设置变更，重建全部账号…      ← 同一无身份线程再重建一次
  11:09:48.110 [onPool-worker-6]  [Face] 账号 'ops' 人脸检测模型未配置   ← 仍是 ops 自己的配置 ✓
```

### 5.3 `verify` 修复：正例 + **三个反例**

修复前：`verify` 是「看最高分那条的 id 是否等于入参 id」。同一张脸被重复登记时
各条相似度都是 1.0，谁排第一取决于向量存储返回顺序 → 对**刚登记**的那条
`/v2/face/verify` 返回 `matched=false`（响应里连 score 都没有），
而同图的 `/v2/face/identify` 命中列表里该 id 的 score 正是 **1.0** —— 同一事实两个端点结论相反。
改为「该 id 是否**命中**」（命中列表已由管线按 `face.match_threshold` 过滤）。

```
正例   verify(id=本次登记, 同图)              → matched=True      （修复前 False）
反例①  verify(id=不存在的 id, 同图)           → 00000 / False     （防「修成恒 true」）
反例②  verify(id=已删除的 id, 同图)           → False
反例③  verify(id=任一 id, 无人脸的图)          → 00000 / False（不 5xx）
对照组 compare(同图,同图)=1.0/True、identify 命中含该 id/score=1.0  —— 检测与特征链路本身正常
```

`/v2/face/verify` 前端零引用（唯一调用方是 `FaceController`），所以语义修正是收敛的。

### 5.4.2 三处判据与直觉相反（都是先写错、再按代码事实纠正的）

1. **删除的期望是 `200 + data=false`，不是 403/404。** `FaceStores.remove` 走当前账号的库
   （`FaceStores.java:300` `st()`），`ops` 的库里没有 `admin` 的 id → 空操作。
   契约上「删不到别人的东西」就是成功。我最初断言成 403，跑出 `FAIL`，查代码后确认
   **是我的断言错了**，`200 + data=false` 恰恰是隔离正确的表现。

   就**常驻**（清理只删条目、不删目录），所以「空库账号不得有目录」同样不成立 ——
   空库账号的判据是「目录若在，必须是自己的、且不含 `admin` 的任何 id」。
   我连续在这里错了两轮（先要求必须存在、再要求必须不存在），两次都是断言问题。
3. **「A 非空 / B 为 0」这套判据依赖 `ops` 恰好是空库，不自洽。** 探针或中断留下的
   脏数据会让它因**历史残留**而非隔离缺陷失败。现在套件开头自建干净基线。

### 5.5.6 本节套件自身踩到并修掉的 4 个缺陷

1. **期望值写成 JSON 的 `false`，实际是 Python 的 `False`** —— `print(False)` 输出 `False`，
   于是 `needLlmConfig`、`available` 连续 3 条恒 FAIL。修法是在取值函数里把 bool 统一小写化，
   而不是把期望值改成 `False`（后者会把「取值口径」和「断言口径」搅在一起）。
2. **`clr` 与 `PUT ""` 语义混用**（见 5.5.5），导致 2 条判据测的根本不是兜底分支。
3. **一个自比自的恒真断言**：`ck "…" "$(win|grep -ac X)" "$(win|grep -ac X)"` —— 写的时候
   想同时打出计数，无意中写成拿自己和自己比，**永远 PASS**。已删掉该行，改成

4. **断言「某用户的覆盖行总数为 0」——在共享环境里必然被别人的合法写入打破。**

   **这不是产品缺陷，也不是套件 bug，是判据的作用域写错了。**

   （`runtime`/`bot`/`image_search`/`face`/`rag`），并在收尾**如实打印作用域之外的行**，

### 6.6 新套件 `verify-store-isolation.sh` 自身的 4 个缺陷（3 个会**假绿**）

写隔离套件时踩到的，性质比 6.1~6.5 更隐蔽 —— **都表现为「PASS」而不是「FAIL」**：

1. **包装函数写死形参，`-X DELETE` 被静默丢弃。** `api_as` 只接 3 个参数，
   多传的 `'-X DELETE'` 被丢掉 → 实际发出 **GET** `/v2/face/<id>` → **恒 200** →
   断言「删除被拒」必然假绿。已改 `"$@" ` 透传。
2. **透传改完后漏了 `"$url"`。** `curl` 报 `no URL specified`，4 次预热调用全废，
   却因为脚本只在**后面**检查 code 而晚了一拍才 FATAL。已修。
   （`prodgrade.sh:46-53` 早就记录过同一个坑，两套件独立踩了一遍。）
3. **`grep -c` 匹配 0 条时「打印 0 且退出码为 1」。** 写成 `grep -c ... || echo 0`
   会得到 `"0\n0"`，`$((LEAK2 + n))` 抛 `arithmetic syntax error`、累加值**停在 0** →
   「目录里不含 admin 的任何 id」这条**蒙对**。已改为只取 `grep` 自身输出 + `case` 兜非数字。
4. **管道里的 python 漏 `import sys`。** `NameError` 被 `except Exception: print('ERR')`
   吞掉，判据永远失败且看不出原因。已改为 **`curl -o` 落盘再 `json.load(open(...))`**，
   出错时能直接看到响应体。另：远端**没有 `bc`**，求和改用 `awk`。

还有一条判据设计缺陷：`ck` 只做等值比较，我却把期望值写成区间 `"1..$N"` 再去比 `2`
和 `1..2` —— **永远不等，恒 FAIL**。已改为先算布尔、再比 `ok`/`bad`。

**这 4 条的共同教训**：判据「有牙」必须**单独证明**，不能因为跑出 PASS 就相信它。
本套件因此附了 §5.4.3 的敏感性反向对照。

### 6.8（2026-10-05 轮）浏览器 11 套的 26 条 FAIL：根因是**令牌密文被当成令牌发出去**

首次跑 11 套得 **142/168，26 条 FAIL**。**连续两遍逐条一致**（同样套件、同样断言数、
同样失败）→ 确定性，不是抖动。再按时间窗取证排除了两个常见假设：

| 假设 | 实测 | 结论 |
|---|---|---|
| 服务在窗口内重启 → 会话被清 | pid 575743 从 01:59:29 到 02:28:25 **未重启**，md5 未变 | 排除 |
| 登录接口限流 / 新登录踢旧会话 | 连打 12 次登录 **12/12 全 200**；3 次登录返回**同一个**令牌（`74d8ab9e…`，与 02:29 那次完全相同）→ 令牌是**确定性**的 | 排除 |

真因（浏览器内实测）：

| 项 | 值 |
|---|---|
| 浏览器登录请求体 | `{"username":"admin","password":"admin123"}` **明文**，与 API 直登完全相同 |
| 服务端下发的**原始**令牌 | **1376** 字符（`74d8ab9e55d9e8b9…`，与 API 直登同一个） |
| `localStorage` 的 `ai-guada:accessToken` | **1856 字符密文**（+480），**不含**原始令牌 |
| 带**原始令牌**请求 `/v2/settings/image_search` | **200** |
| 带**密文**请求同一路径 | **403 `A0403S0000` 用户信息不存在/请重新登录** |
| 头名是否有关 | **无关**：`x-oauth-token` 与 `Authorization: Bearer` 都是 403 |
| 补指纹头（`x-req-fingerprint`）/ Referer | 无效，仍 403 |

即：**框架 storage 是加密落盘的**，而 9 套用例都是
`localStorage.getItem('ai-guada:accessToken')` 直接当令牌发出去 —— **发的是密文**。
真用户不受影响，因为应用自己走框架 storage API 会解密；
报错文案「用户信息不存在 / 请重新登录」极具误导性，看着像产品坏了。

### 8.1 数据库访问：三个坑，每个都让我产出过「空输出」

收尾核验时连查三次空输出才查对，**空输出被当成了「表不存在」**。这属于 §6 同一类
「误导性结论」，故单列。

| 项 | 正确值 |
|---|---|
| 库 | **`ai_test`**（不是 `ai_guada`；`oauth` 是用户域，73 张业务表在 `ai_test`） |
| 连法 | `mysql -N -B -h 127.0.0.1 -P 3306 -u ai -pai ai_test -e '…'` —— **不需要 sudo** |
| 列名 | **每列都带表名前缀**：`sys_database_version_success`、`sys_ai_global_setting_value`、`sys_ai_user_setting_user_id`… |

三个坑：

1. **root 走 unix_socket 的 `SHOW DATABASES` 里根本没有 `ai_test`。**
   照它判断会得出「表不存在」。库的权威答案在**服务自己的启动参数**里：
   `systemctl cat ai-starter | grep -o 'spring.datasource.url=[^ ]*'`。
2. **`mysql -N -B -- "$DB" -e …` 里的 `--` 不是合法参数**，mysql 会打 3000 行用法。
   正确写法是 `mysql -N -B "$DB" -e …`。
3. **`echo ai | sudo -S mysql …` 会把库用户名当 sudo 口令**（口令是 `kali`），
   得到 `sudo: no password was provided` + `1 incorrect password attempt`。
   叠加 `2>/dev/null` 就彻底静默 —— 正是「空输出」的来源。

**由此定一条纪律**：**判据连不上库时，先做连通性自检再解读结果**，
即先断言 `SELECT DATABASE()` 与表总数非零，然后才允许把查询结果当证据。
`2>/dev/null` 只可用于「已经自检过」的路径。

> 附一条正面证据：`sys_ai_user_setting` 的 `user_id` 存的是**用户名**而非数字 id。
