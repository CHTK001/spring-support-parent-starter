### 5.2 用户改默认模型后**立即生效** + **污染防护**

正确的不变量**不是**「共享单例从不重建」，而是「重建必须发生在**无身份线程**」：

```
ops PUT face.detector_model="" →
  11:09:48.009 [cat-handler-126]  [SysAiUserSetting] 用户 ops 覆盖已写入
  11:09:48.010 [cat-handler-126]  [Face] 人脸设置变更（用户级）…        ← 同一请求线程，事件由用户写入发出
  11:09:48.025 [cat-handler-126]  [Face] 账号 'ops' 人脸检测模型未配置   ← 按 ops 自己的配置
  11:09:48.070 [cat-handler-126]  [Face] 账号 'admin' 人脸库就绪 3/3 条  ← admin 未被波及
  11:09:48.077 [onPool-worker-6]  [FaceClientManager] 开始热重建          ← **无身份异步线程**（读全局，不污染）
  11:09:48.100 [onPool-worker-6]  [Face] 人脸设置变更，重建全部账号…      ← 同一无身份线程再重建一次
  11:09:48.110 [onPool-worker-6]  [Face] 账号 'ops' 人脸检测模型未配置   ← 仍是 ops 自己的配置 ✓
  11:09:48.144 [onPool-worker-6]  [Face] 账号 'admin' 人脸库就绪 3/3 条  ← 仍未串号 ✓

【判定①】ops 被判「未配置」2 次、admin 就绪 2 次      （两个来源各一次，各自绑定正确）
【判定②】共享单例重建出现在**请求线程**0 次、无身份异步线程 2 次  （0 次请求线程 = 无污染）
读层：ops detector=''   admin detector='scrfd-face-detector'
```

两条链路各司其职：用户级写入 → 按账号重建（每个账号绑自己的身份）；
`SettingsController.publishUserSettingsChanged` 在**无请求身份的新线程**发一次全局事件 →
共享单例按**全局**配置重建。**关键**：第二个来源能在多账号上仍然正确，是因为
`FaceStores.AccountFace.reload` 对每个账号做了 `AiUserContext.runWith(该账号)`
（`9b56a645d`）—— 否则无身份线程会把**所有**账号都按全局配置建，用户的配置等于没生效。

### 5.3 `verify` 修复：正例 + **三个反例**

修复前：`verify` 是「看最高分那条的 id 是否等于入参 id」。同一张脸被重复登记时
各条相似度都是 1.0，谁排第一取决于向量存储返回顺序 → 对**刚登记**的那条
`/v2/face/verify` 返回 `matched=false`（响应里连 score 都没有），
而同图的 `/v2/face/identify` 命中列表里该 id 的 score 正是 **1.0** —— 同一事实两个端点结论相反。
改为「该 id 是否**命中**」（命中列表已由管线按 `face.match_threshold` 过滤）。

```
正例   verify(id=本次登记, 同图)              → matched=True      （修复前 False）
反例①  verify(id=不存在的 id, 同图)           → 00000 / False     （防「修成恒 true」）
反例②  verify(id=已删除的 id, 同图)           → False
反例③  verify(id=任一 id, 无人脸的图)          → 00000 / False（不 5xx）
对照组 compare(同图,同图)=1.0/True、identify 命中含该 id/score=1.0  —— 检测与特征链路本身正常
```

`/v2/face/verify` 前端零引用（唯一调用方是 `FaceController`），所以语义修正是收敛的。

## 六、本轮修掉的「验收工具自身」缺陷（都会产出**误导性结论**）

在共享环境里，**工具的 bug 与产品的 bug 同样致命** —— 前者会把坏的报成好的，或反过来。
本轮三个，全部实测踩到并修掉：

### 6.1 验收脚本原本在仓库外，没有版本控制

`D:\ch\project\.run\deploy\` **不在任何 git 仓库的工作树内**（`D:\ch\project\.run` 位于两个仓库之外）。
按 AGENTS「未提交的改动不构成交付物」：脚本与结论随时会丢。
已按 monitor-starter 先例收进 **`spring-support-ai-starter/src/acceptance/`** 并提交，
含 `README.md`（运行手册 + 判据纪律 + 环境坑）。

### 6.2 清理脚本无条件删表 → 删掉了**别人的**数据

`cleanup-final-state.sh` 原为 `DELETE FROM sys_ai_user_setting;`，实测把**另一会话**正在用的
`tester | runtime | default_model | agnes:agnes-2.5-flash` 一起删了。
已**还原该行**，并改为只删**白名单**里的 `(用户,分组,字段)`；剩余非 0 时明确提示
「可能是别人的行，不得再删」。当前剩余 1 行 = 他人的 `tester` 行（保留 ✓）。

### 6.3 `verify-secfix.sh` 读到**上一轮的旧结果**，产出假绿

服务不可达时它一路跑完：`HTTP=000`、响应体根本没写出来，`code()` 于是读到
**上一轮遗留的 `/tmp/sf*.json`**，打印出「403 仅管理员可修改」「200 操作成功」——
**一份服务已经挂了却全绿的假报告**。已改：拿不到令牌立即 FATAL；
每次请求前 `rm` 输出文件；`HTTP=000` 明确报「连不上，不得据此判定权限」。

### 6.4 `facegrade.sh` 的「假红」：探针坏了，产品是对的

`sudo_()` 定义在使用点**之后**（L174 vs L129/L139），探「库是否为空」时命令不存在、
输出为空，`${BEFORE_N:-0}` 退化成 `"0"` → **把非空库判成空库** → 在 2 条记录的库上断言
「空库应 matched=false」。已改：判空走 **API**（`GET /v2/face/list`）且读不到一律回 `ERR`
（绝不回 0）；admin 库非空时改用空库账号 `ops` 验证，**而不是跳过**
（跳过等于这条防 NPE 的覆盖在真实环境里永远不跑）。

### 6.5 并发重启造成的误导性失败

机器 09:20 重启过（`/tmp` 被清空），且**其他会话**在 10:45~10:58 反复重启同一服务
（systemd 日志可见 4 次 Stopped/Started）。我的套件撞上重启窗口，拿到
`[FATAL] 未取得令牌` —— 而我的输出过滤又把这个失败吃掉了，看起来像「无输出」。
已改：两套件**先等就绪（`/v1/captcha` 200）+ 登录重试**，等满仍失败才 FATAL；
运行器**无条件打印末尾几行**，不再让过滤器吃掉失败。

代码路径完整保留（事件默认 `userScoped=false`），但**未端到端跑到**，不当作已验证。
