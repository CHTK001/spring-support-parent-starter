### 5.2 用户改默认模型后**立即生效** + **污染防护**

正确的不变量**不是**「共享单例从不重建」，而是「重建必须发生在**无身份线程**」：

```
ops PUT face.detector_model="" →
  11:09:48.009 [cat-handler-126]  [SysAiUserSetting] 用户 ops 覆盖已写入
  11:09:48.010 [cat-handler-126]  [Face] 人脸设置变更（用户级）…        ← 同一请求线程，事件由用户写入发出
  11:09:48.025 [cat-handler-126]  [Face] 账号 'ops' 人脸检测模型未配置   ← 按 ops 自己的配置
  11:09:48.070 [cat-handler-126]  [Face] 账号 'admin' 人脸库就绪 3/3 条  ← admin 未被波及
  11:09:48.077 [onPool-worker-6]  [FaceClientManager] 开始热重建          ← **无身份异步线程**（读全局，不污染）
  11:09:48.100 [onPool-worker-6]  [Face] 人脸设置变更，重建全部账号…      ← 同一无身份线程再重建一次
  11:09:48.110 [onPool-worker-6]  [Face] 账号 'ops' 人脸检测模型未配置   ← 仍是 ops 自己的配置 ✓

【判定①】ops 被判「未配置」2 次、admin 就绪 2 次      （两个来源各一次，各自绑定正确）
【判定②】共享单例重建出现在**请求线程**0 次、无身份异步线程 2 次  （0 次请求线程 = 无污染）
读层：ops detector=''   admin detector='scrfd-face-detector'
```

两条链路各司其职：用户级写入 → 按账号重建（每个账号绑自己的身份）；
`SettingsController.publishUserSettingsChanged` 在**无请求身份的新线程**发一次全局事件 →
共享单例按**全局**配置重建。**关键**：第二个来源能在多账号上仍然正确，是因为
`FaceStores.AccountFace.reload` 对每个账号做了 `AiUserContext.runWith(该账号)`
（`9b56a645d`）—— 否则无身份线程会把**所有**账号都按全局配置建，用户的配置等于没生效。

### 5.3 `verify` 修复：正例 + **三个反例**

修复前：`verify` 是「看最高分那条的 id 是否等于入参 id」。同一张脸被重复登记时
各条相似度都是 1.0，谁排第一取决于向量存储返回顺序 → 对**刚登记**的那条
`/v2/face/verify` 返回 `matched=false`（响应里连 score 都没有），
而同图的 `/v2/face/identify` 命中列表里该 id 的 score 正是 **1.0** —— 同一事实两个端点结论相反。
改为「该 id 是否**命中**」（命中列表已由管线按 `face.match_threshold` 过滤）。

```
正例   verify(id=本次登记, 同图)              → matched=True      （修复前 False）
反例①  verify(id=不存在的 id, 同图)           → 00000 / False     （防「修成恒 true」）
反例②  verify(id=已删除的 id, 同图)           → False
反例③  verify(id=任一 id, 无人脸的图)          → 00000 / False（不 5xx）
对照组 compare(同图,同图)=1.0/True、identify 命中含该 id/score=1.0  —— 检测与特征链路本身正常
```

`/v2/face/verify` 前端零引用（唯一调用方是 `FaceController`），所以语义修正是收敛的。

### 5.4.1 为什么必须单独立一套

人脸与以图搜图原先**共用一份全局 jvector 索引**（`<CWD>/face/face-index`、
`<base>/image-search-store`）。这种形态下 `prodgrade.sh` / `facegrade.sh` 是**全绿**的
—— 功能都能用，但 A 账号的数据 B 账号能看到。**隔离的判据不是「功能能用」，
而是「A 的数据 B 拿不到」**，原有 108 条判据里没有一条能抓到它。

新增 `verify-store-isolation.sh`，6 组，**PASS=22 FAIL=0**（2026-10-05 实测）：

| 组 | 判据 | 实测 |
|---|---|---|
| 0 | 基线归零 + 预热：先清空 `ops` 底库，再让两账号各访问一次列表 | `ops` 归零后为空 |
| 1 | 目录归属：有数据的账号目录必须存在；**无全局单份** `face/face-index`；旧版 `image-search-store` 已归位 | `admin/face`、`admin/imagesearch`、`ops/face` 均在；全局单份 `absent` |
| 2 | 人脸列表跨账号不可见 | `admin=3`、`ops=0` |
| 3 | 索引文件只在 `<账号>/face/` 下；`ops` 快照不含 `admin` 的任何 id | 无游离 `face-index.vectors`；泄漏计数 `0` |
| 4 | 删除不串号：`ops` 删 `admin` 的 id | `HTTP=200 data=false`，`admin` 条数仍 `3`、该 id 仍在 |
| 5 | 以图搜图列表跨账号不可见 | `admin=2`、`ops=0` |
| 6 | **写入侧按 userId 建库**：`ops` 落库后建出自己的索引库，且 `admin` 不受影响 | `ops/imagesearch/index.json` 生成；`admin` 仍 `2`；`ops` 检索只命中自己那 `1` 条 |

第 6 组是这套件的核心 —— 前 5 组都靠「`ops` 是空的」来证明隔离，第 6 组**正面证明**
`ops` 写入时建的是**它自己**的索引库。改造前两者共用一份索引，这一组会直接失败。

### 5.4.2 三处判据与直觉相反（都是先写错、再按代码事实纠正的）

1. **删除的期望是 `200 + data=false`，不是 403/404。** `FaceStores.remove` 走当前账号的库
   （`FaceStores.java:300` `st()`），`ops` 的库里没有 `admin` 的 id → 空操作。
   契约上「删不到别人的东西」就是成功。我最初断言成 403，跑出 `FAIL`，查代码后确认
   **是我的断言错了**，`200 + data=false` 恰恰是隔离正确的表现。
2. **目录要求按「该账号该功能是否真有数据」区分。** 人脸库**急**创建，以图搜图**惰**创建
   （`ImageSearchStore.java:141`「目录只在首次写入/删除时才创建」）。而且目录一旦建过
   就**常驻**（清理只删条目、不删目录），所以「空库账号不得有目录」同样不成立 ——
   空库账号的判据是「目录若在，必须是自己的、且不含 `admin` 的任何 id」。
   我连续在这里错了两轮（先要求必须存在、再要求必须不存在），两次都是断言问题。
3. **「A 非空 / B 为 0」这套判据依赖 `ops` 恰好是空库，不自洽。** 探针或中断留下的
   脏数据会让它因**历史残留**而非隔离缺陷失败。现在套件开头自建干净基线。

| ④ 连接器>bot>默认 | `POST /v2/chat/send` → `ChatSendController:116 resolvedModel()` → `EffectiveChatModelResolver.candidates()`，每档未命中注册表即打一条 `[ModelResolver] 候选模型 X 未在本供应商注册`（`EffectiveChatModelResolver:192`） | 日志**先后顺序**即优先级 |
| ⑤ 知识库 rag | `GET /v2/rag/status` 的 `data.config.llm_model`（按账号生效值）与 `data.needLlmConfig`（为 true 正是 `RagClientManager:725` 走兜底分支的条件） | 直接回显 |
| ① 隔离不变量 | 收尾断言 admin 的 rag / 以图搜图取值未被 ops 污染 | 回归 |

**④ 的判据设计是本节的关键**：`addCandidate` 对每一档都是**急切**查
`sys_ai_provider_model(enabled=1)` 并**按调用顺序**打日志。所以给 bot / runtime 两档各放一个
**不同的假模型名**，两条日志的先后顺序就直接等于优先级顺序 —— 不需要真的调用模型，
也不需要往注册表塞数据。这比「看解析结果等于谁」更硬：它不依赖任何一档恰好可用。

### 5.5.3 各条的判据与**敏感性对照**（判据必须有牙）

- **②** 三段：ops 无覆盖时命中全局 `image_search` 组（`cn-clip-rn50-image`）；ops 自配后
  `status.model` 跟随 ops（`zprobe-image-own`）；★把 tier-1 写成**空值覆盖行**后，
  `status.model` 必须等于 ops 自己 runtime 档的特征值 `zprobe-img-fallback`。
  **对照**：两档皆空时 `available` 必须转 `false` —— 反证上一次确实靠兜底撑住，不是巧合。
- **④** `zprobe-bogus-bot-1` 的日志行（L10）先于 `zprobe-bogus-run-1`（L11）。
  ★**换位对照**：把两个假名对调后重跑，顺序**跟着翻转**（`run-2` L10 先于 `bot-2` L11）。
  若实现里 runtime 档其实排在 bot 之前，这一条必然 FAIL。
  附带钉住一个前提：解析发生在无身份异步线程 `[nPool-worker-23]` 上，**却仍读到 ops 的覆盖值**
  —— 说明 `AiUserContext` 跨线程传递有效。否则两个只存在于 ops 的标记根本不会出现在日志里，
  判据会因「标记缺失」直接 FAIL。
- **⑤** ops 自配 `agnes:agnes-3.0-flash` 后按账号生效，而 admin 仍为全局
  `agnes:agnes-2.0-flash`（隔离不变量）。★把 tier-1 写成空值覆盖行后 `needLlmConfig=true`
  且 `llm_model` 为空，即兜底分支条件成立。
  **对照**：改用 `DELETE .../overrides`（删行）后立刻回落全局 `agnes:agnes-2.0-flash`、
  `needLlmConfig=false` —— 这一条把「空值覆盖行」与「删行」两种语义分开钉死（见 5.5.5）。

### 5.5.4 观测边界（如实记录，不假装验过）

**规格 ⑤ 兜底后解析出的具体模型名，无法按普通账号观测。** 打出该值的日志在
`RagClientManager:732`（`[RagClientManager] RAG 生成式回答使用对话模型: account={}, model={}`），
但触发它的 `resolveDelegate()` 只挂在 `RagController.query` 上，而该方法带
`@Permission("admin")`（`RagController:256`，实测 ops 调用返回
`{"code":"S0503C0000","msg":"权限不足，需要：admin"}`）。

所以本节对 ⑤ 只声称两件事：**按账号隔离成立**、**兜底分支的触发条件成立**。
「兜底后到底选了哪个模型」**没有**端到端跑到，不计入结论。

### 5.5.5 顺带钉死的一个语义（此前无任何判据覆盖）

用户级覆盖有两种「空」，语义**不同**，此前没有被任何判据区分过：

| 操作 | 库里的效果 | `GlobalSettingReader.getStrAs` 的结果 |
|---|---|---|
| `PUT /v2/settings/{group}` 传 `""` | 留下一个**空值行** | 返回 `""`，**不回落全局** |
| `DELETE /v2/settings/{group}/overrides` | **删行** | 无行 → **回落全局** |

本节的 ②⑤ 判据正是靠这个差异，才在**不修改任何全局配置**的前提下验到了兜底分支
（共享环境里改全局配置会影响他人，不能做）。这也解释了为什么套件第一版用 `clr` 去构造
「tier-1 为空」的场景是错的 —— 删了行就等于回落全局，测到的不是兜底。

### 5.5.6 本节套件自身踩到并修掉的 3 个缺陷

1. **期望值写成 JSON 的 `false`，实际是 Python 的 `False`** —— `print(False)` 输出 `False`，
   于是 `needLlmConfig`、`available` 连续 3 条恒 FAIL。修法是在取值函数里把 bool 统一小写化，
   而不是把期望值改成 `False`（后者会把「取值口径」和「断言口径」搅在一起）。
2. **`clr` 与 `PUT ""` 语义混用**（见 5.5.5），导致 2 条判据测的根本不是兜底分支。
3. **一个自比自的恒真断言**：`ck "…" "$(win|grep -ac X)" "$(win|grep -ac X)"` —— 写的时候
   想同时打出计数，无意中写成拿自己和自己比，**永远 PASS**。已删掉该行，改成
   「两档皆空 → `available=false`」这条真有因果的对照。

### 5.5.7 验收期间的并发事实（如实记录）

- 跑这套件期间，**别的会话**在 `sys_ai_user_setting` 插入了
  `admin | session | ai_next_task_enabled | true` 一行，并在工作树里给
  `SettingsController.USER_WRITABLE_GROUPS` 加了 `"session"`。
  该改动**未触及** `USER_MODEL_GROUPS` / `isUserScopedGroup`，故规格 ① 不受影响。
- `tester | runtime | default_model | agnes:agnes-2.5-flash` 这一行**全程未被本套件改动**，
  套件开头与结尾都断言了它的行数。
- 本套件只清 ops 自己的覆盖行（`DELETE ... WHERE user_id='ops'`），**没有任何全表删除**。

## 六、本轮修掉的「验收工具自身」缺陷（都会产出**误导性结论**）

在共享环境里，**工具的 bug 与产品的 bug 同样致命** —— 前者会把坏的报成好的，或反过来。
本轮三个，全部实测踩到并修掉：

### 6.1 验收脚本原本在仓库外，没有版本控制

`D:\ch\project\.run\deploy\` **不在任何 git 仓库的工作树内**（`D:\ch\project\.run` 位于两个仓库之外）。
按 AGENTS「未提交的改动不构成交付物」：脚本与结论随时会丢。
已按 monitor-starter 先例收进 **`spring-support-ai-starter/src/acceptance/`** 并提交，
含 `README.md`（运行手册 + 判据纪律 + 环境坑）。

### 6.2 清理脚本无条件删表 → 删掉了**别人的**数据

`cleanup-final-state.sh` 原为 `DELETE FROM sys_ai_user_setting;`，实测把**另一会话**正在用的
`tester | runtime | default_model | agnes:agnes-2.5-flash` 一起删了。
已**还原该行**，并改为只删**白名单**里的 `(用户,分组,字段)`；剩余非 0 时明确提示
「可能是别人的行，不得再删」。当前剩余 1 行 = 他人的 `tester` 行（保留 ✓）。

### 6.3 `verify-secfix.sh` 读到**上一轮的旧结果**，产出假绿

服务不可达时它一路跑完：`HTTP=000`、响应体根本没写出来，`code()` 于是读到
**上一轮遗留的 `/tmp/sf*.json`**，打印出「403 仅管理员可修改」「200 操作成功」——
**一份服务已经挂了却全绿的假报告**。已改：拿不到令牌立即 FATAL；
每次请求前 `rm` 输出文件；`HTTP=000` 明确报「连不上，不得据此判定权限」。

### 6.4 `facegrade.sh` 的「假红」：探针坏了，产品是对的

`sudo_()` 定义在使用点**之后**（L174 vs L129/L139），探「库是否为空」时命令不存在、
输出为空，`${BEFORE_N:-0}` 退化成 `"0"` → **把非空库判成空库** → 在 2 条记录的库上断言
「空库应 matched=false」。已改：判空走 **API**（`GET /v2/face/list`）且读不到一律回 `ERR`
（绝不回 0）；admin 库非空时改用空库账号 `ops` 验证，**而不是跳过**
（跳过等于这条防 NPE 的覆盖在真实环境里永远不跑）。

### 6.5 并发重启造成的误导性失败

机器 09:20 重启过（`/tmp` 被清空），且**其他会话**在 10:45~10:58 反复重启同一服务
（systemd 日志可见 4 次 Stopped/Started）。我的套件撞上重启窗口，拿到
`[FATAL] 未取得令牌` —— 而我的输出过滤又把这个失败吃掉了，看起来像「无输出」。
已改：两套件**先等就绪（`/v1/captcha` 200）+ 登录重试**，等满仍失败才 FATAL；
运行器**无条件打印末尾几行**，不再让过滤器吃掉失败。

### 6.6 新套件 `verify-store-isolation.sh` 自身的 4 个缺陷（3 个会**假绿**）

写隔离套件时踩到的，性质比 6.1~6.5 更隐蔽 —— **都表现为「PASS」而不是「FAIL」**：

1. **包装函数写死形参，`-X DELETE` 被静默丢弃。** `api_as` 只接 3 个参数，
   多传的 `'-X DELETE'` 被丢掉 → 实际发出 **GET** `/v2/face/<id>` → **恒 200** →
   断言「删除被拒」必然假绿。已改 `"$@" ` 透传。
2. **透传改完后漏了 `"$url"`。** `curl` 报 `no URL specified`，4 次预热调用全废，
   却因为脚本只在**后面**检查 code 而晚了一拍才 FATAL。已修。
   （`prodgrade.sh:46-53` 早就记录过同一个坑，两套件独立踩了一遍。）
3. **`grep -c` 匹配 0 条时「打印 0 且退出码为 1」。** 写成 `grep -c ... || echo 0`
   会得到 `"0\n0"`，`$((LEAK2 + n))` 抛 `arithmetic syntax error`、累加值**停在 0** →
   「目录里不含 admin 的任何 id」这条**蒙对**。已改为只取 `grep` 自身输出 + `case` 兜非数字。
4. **管道里的 python 漏 `import sys`。** `NameError` 被 `except Exception: print('ERR')`
   吞掉，判据永远失败且看不出原因。已改为 **`curl -o` 落盘再 `json.load(open(...))`**，
   出错时能直接看到响应体。另：远端**没有 `bc`**，求和改用 `awk`。

还有一条判据设计缺陷：`ck` 只做等值比较，我却把期望值写成区间 `"1..$N"` 再去比 `2`
和 `1..2` —— **永远不等，恒 FAIL**。已改为先算布尔、再比 `ok`/`bad`。

**这 4 条的共同教训**：判据「有牙」必须**单独证明**，不能因为跑出 PASS 就相信它。
本套件因此附了 §5.4.3 的敏感性反向对照。
