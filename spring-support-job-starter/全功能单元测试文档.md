> 本模块的全业务功能验证一律采用 **启动 Spring 服务测接口 / 驱动真实业务链路** 的方式
> （`mvn spring-boot:run` 或 `java -cp` 启动真实应用，三模式 SINGLE / SCHEDULER / EXECUTOR 分别起服务，

## 2. 全业务验证方式：启动 Spring 服务

「全功能」不以 mock 断言覆盖，而以**真实启动 Spring 上下文**驱动各功能点。

三个可执行应用（均在本模块 `src/main/java/com/chua/starter/job/`）：
- `JobSingleApplication` → SINGLE 单机闭环
- `JobSchedulerApplication` → SCHEDULER 调度中心（Leader + 8081 长链监听）
- `JobExecutorApplication` → EXECUTOR 执行器（连调度中心）

示例任务 `example/DemoJobs.java`：`@Job("example.hello", cron "0/1 * * * * ?")` 成功计数、
`@Job("example.fail")` 故意抛异常、`@Scheduled(cron "0/1 * * * * ?")` 原生定时计数。

### 2.1 `mvn spring-boot:run` 方式

```bash
# 需显式指定 main-class（本模块含 3 个 main）+ 覆盖父 POM 的 skipTests
mvn spring-boot:run "-Dspring-boot.run.main-class=com.chua.starter.job.JobSingleApplication"
```

> 注意：`spring-boot:run` 会 fork 一个 java 子进程，非 TTY 下 stdout 不落回控制台；
> 且 `-Dspring-boot.run.arguments` 传 `--xxx` 形式易被解析为 maven 选项报 `Unrecognized option`。
> 稳妥做法见 2.2 的 `java -cp` 直跑。

### 2.2 `java -cp` 直跑方式（推荐，已实际用于验证）

先生成全量运行时 classpath：

```bash
mvn dependency:build-classpath "-Dmdep.includeScope=runtime" "-Dmdep.outputFile=%TEMP%\opencode\job-cp.txt"
```

再分别启动三模式（SINGLE 为例）：

```powershell
$cp = Get-Content "$env:TEMP\opencode\job-cp.txt" -Raw
$classes = "G:\work\spring-support-parent-starter\spring-support-job-starter\target\classes"
java.exe -cp "$classes;$cp" com.chua.starter.job.JobSingleApplication `
  --plugin.job.enable=true --plugin.job.role=SINGLE --plugin.job.cluster.group=demo-single `
  --logging.level.com.chua.starter.job=DEBUG
```

**SCHEDULER**（注意 `sync.scheduler` 是嵌套对象，必须用子属性传参）：

```powershell
java.exe -cp "$classes;$cp" com.chua.starter.job.JobSchedulerApplication `
  --plugin.job.enable=true --plugin.job.role=SCHEDULER --plugin.job.cluster.group=demo-scheduler `
  --plugin.job.sync.scheduler.listen-host=0.0.0.0 --plugin.job.sync.scheduler.listen-port=8081 `
  --logging.level.com.chua.starter.job=DEBUG
```

**EXECUTOR**：

```powershell
java.exe -cp "$classes;$cp" com.chua.starter.job.JobExecutorApplication `
  --plugin.job.enable=true --plugin.job.role=EXECUTOR --plugin.job.cluster.group=demo-pair `
  --plugin.job.sync.executor.server-url=http://127.0.0.1:8081 `
  --logging.level.com.chua.starter.job=DEBUG
```

### 3.5 并发 / 吞吐专项压测（✅）

> 独立压测应用，验证执行线程池 (`pool.core-size/max-size`) 的并发上限与线性吞吐。
> 数据来自 SINGLE 单进程内 Leader→Executor 闭环。脚本：`run-cc.ps1`（并发）、`run-tp.ps1`（吞吐，临时目录）。

**并发压测**（`example.cc.01~12`，12 任务每秒同峰，每任务 `sleep 1500ms` 制造重叠，共享原子计数 `concurrentMax`）：

| core=max | 注册处理器 | 并发峰值 max | 线程集合 | 结论 |
|---|---|---|---|---|
| 8 | 18 | **8** | job-exec-1~8 | 打满 core，无超发线程 |
| 16 | 18 | **16** | job-exec-1~16 | 线程池按 max 正常扩容，未拒绝 |

**吞吐压测**（`example.tp.01~24`，24 任务每秒同峰，每任务 `sleep 500ms`；请求率恒定 24 件/s，稳定窗口去头尾 3s）：

| core=max | 请求率 | 稳定窗口吞吐 | 理论上限 | 结论 |
|---|---|---|---|---|
| 8 | 24 件/s | **16.0 完成/s** | 2×8=16/s | 线程饱和，恰好用满 |
| 16 | 24 件/s | **23.3 完成/s** | 2×16=32/s | 扩容→吞吐近乎翻倍，触请求率上限 |
| 32 | 24 件/s | **24.1 完成/s** | 2×32=64/s | 吞吐受请求率 24 件/s 封顶 |

> 结论：并发≤max 时以 `core` 为实际并发上限；吞吐与服务耗时相关（500ms→每线程 2 件/s），
> 扩容 `core-size` 使吞吐线性提升直至达到任务请求率瓶颈，期间队列 (`queue-size`) 无拒无丢。

**线程池上限（`PoolMaxProbe`，core=8/max=32/queue=10 + AbortPolicy，突发 300 任务 × 300ms）**：

| 指标 | 实测 | 期望 | 结论 |
|---|---|---|---|
| `largestPoolSize` | **32** | max=32 | `LinkedBlockingQueue` 填满后弹性扩容至最大线程数，**max 封顶生效** |
| `activeMax` | **32** | max=32 | 实际并发执行峰值打满 max |
| `rejected` | **258** | 300-(32+10)=258 | 打满 max+queue 后 `AbortPolicy` 拒绝第 43 起及以后的任务，计数精确 |

> 关键机制：`buildExecutor()` 用 `LinkedBlockingQueue(queue-size)`，线程不是"先扩 max 再排队"，而是
> **core 全忙 → 先入队 → 队列填满后才扩线程至 max → 再满则 AbortPolicy 拒绝**。
> 因此默认 `queue=128` 下并发/吞吐测试队列仅在微小突发时短暂缓冲，随机突发到 128+ 才会露 max 上限；大队列（如旧默认 1000）会吞掉扩容弹性、线程恒等于 core。

**虚拟线程（`pool.virtual=true`，默认开启，`VtProbe` 实测）**：

| 执行器 | 300 件 × 500ms 总耗时 | 吞吐 | 并发峰值 |
|---|---|---|---|
| 平台线程 core/max=32 | 5014ms | 60 件/s | 32 |
| 虚拟线程 per-task | **551ms** | **544 件/s** | **300** |

> 提速 **9.1×**。吞吐量应用实测（`job.tp.01~24`，24 件/s × 500ms）：虚拟线程默认开启下稳定 **24.05 完成/s**
> 且队列无积压、无丢单，执行线程全部为 `virtual-*`（平台线程 `job-exec-*` 零占用），突破了
> 平台线程"线程数÷耗时"的硬上限。适合阻塞型任务（sleep/RPC/DB/IO）；CPU 密集型任务无阻塞让位，不推荐虚拟线程。
> `pool.virtual=false` 可回退平台线程池，兼容旧配置。

**本机承载能力实测（`VtLimitProbe`，i5-12600KF = 10 核 16 逻辑线程 / 32GB）**：

| 任务类型 | 同时运行上限 | 实测数据 |
|---|---|---|
| 阻塞型（sleep/IO/RPC/DB，定时任务主流） | 实测 **20000 件同时挂起**无压力 | 20000×500ms 并发峰值=20000，总耗时仅 574ms（≈34,843 件/s） |
| CPU 密集（纯计算，无阻塞让位） | **16**（=逻辑核心数，硬上限） | 10000×300 万次忙循环，并发峰值恰为 16 |

> **结论**：阻塞型定时任务并发量主要由 JVM 堆内存决定、与 CPU 核数无关（本机两万级轻松打满，
> carrier 线程大量空闲）；CPU 密集型任务真实并行极限等于逻辑核心数。默认 `pool.virtual=true`
> 对阻塞型已是"无并发上限"形态，生产无需再调 max-size/queue。

## 4. 覆盖缺口分析（对照业务功能清单）

**核心修复回顾**：初期 EXECUTOR 侧日志为
`[job] 未找到 SyncClient SPI 实现, fallback 到 InMemorySyncClient`。根因是
`TcpSyncClient` **没有无参构造函数**（仅 `(String serverUrl)` / `(String clientId, String serverUrl)`），
仓库 SPI 的 `getExtension("tcp")` 用无参实例化失败 → 返回 null → 兜底到内存替身，导致 EXECUTOR 无法
真正连上 SCHEDULER 的 8081（SCHEDULER `getConnectedClients()=[] size=0`）。
已在 `JobAutoConfiguration.jobSyncClient()` 修复：SPI 未命中有效实现时，直接用配置的
`server-url` `new TcpSyncClient(serverUrl)` 装配真实网络客户端（与 SCHEDULER 侧拿 TcpSyncServer 后注入监听地址对称）。
现双进程（SCHEDULER 8081 ⊕ EXECUTOR）已端到端打通双向长链。

| 缺口编号 | 缺失业务功能点 | 状态 |
|----------|----------------|------|

## 5. 三层服务验证全景

```
┌─────────────── 启动 Spring 服务 (java -cp / spring-boot:run) ─────────────┐
│                                                                           │
│  SINGLE:    LeaderLoop ──publish job-cmd──▶ 本地 Bus ──▶ JobExecutor ──▶ handler │
│                                                                           │
│  SCHEDULER: LeaderLoop ──publish job-cmd──▶ SyncServer(0.0.0.0:8081)      │
│                                                │                          │
│                                  真实长链(已通) │ 下行 cmd / 上行 REGISTER │
│                                                ▼                          │
│  EXECUTOR:  TcpSyncClient ──▶ Bus ──▶ JobExecutor ──▶ handler ──send job-log─▶│
└───────────────────────────────────────────────────────────────────────────┘
```

- **SINGLE**: 全进程内，Leader 自选、单秒扫描、本地执行、本地日志。**已验证闭环。**
- **SCHEDULER**: Leader 自选 + 单秒扫描仓库 + 往 `SyncServer(8081)` 推 cmd，`getConnectedClients() size=1` 后按单 client 下发。**已验证。**
- **EXECUTOR**: 真实 `TcpSyncClient`(tcp://127.0.0.1:8081) 订阅 + 派发 + 执行 + REGISTER 上行 + 断线重连。**已实证闭环。**
- **实时网络**: 跨进程 TCP 下行 cmd、上行 TASK_LOG、上行 REGISTER、断线重连已端到端实证（见 3.3 / 缺口表）。

## 6. 已知约束与约定

- **`sync.scheduler` / `sync.executor` 是嵌套配置对象**，命令行传参必须用子属性
  （如 `--plugin.job.sync.scheduler.listen-port=8081`），不能传 `--plugin.job.sync.scheduler=0.0.0.0:8081`——
  后者会因找不到 `String→SchedulerConfig` 转换器而 `APPLICATION FAILED TO START`。
- **`SyncServer.send` 参数顺序**固定为 `(clientId, topic, message)`；sticky 单播若误传
  `(topic, clientId, message)` 会把 clientId 与 topic 互换导致派发落空。
- **本模块无 web 依赖**：`MessageConverterWebMvcConfigurer`（来自 common-starter）需要 webmvc 类，
  缺失时仅产生 warning，不影响 SINGLE/SCHEDULER/EXECUTOR 以 `java -cp` 方式启动成功。
- 父 POM 默认 `<skipTests>true</skipTests>`；若仍要跑任何 test 需 `-DskipTests=false`。
- MyBatis-Plus 仓库 / 选主 / 落库为可选手柄：多数据源不可用时以内存把关，真实库由
  `spring-support-mybatis-starter` 提供扩展（见`架构图.md`）。
- **EXECUTOR 真实长链需真实 `SyncClient` SPI 实现**，当前 fallback 到 `InMemorySyncClient`，
  这是「覆盖是否全」结论的关键约束点。
