## 4. 过程中修掉的缺陷（都是先出产物/先跑通，再被证据打出来的）

**数据质量（抽查才发现）**

1. 拼音：源数据把 -ng 的 g 写成 U+0261 ɡ（3500 字里 773 次）→ 会得到「dīnɡ」，已修正为 g。
2. 拼音白名单漏了带调元音（只留 ü 系列）→ 14 个字读音被清空；改为按 Unicode 名判定拉丁字母。
3. 结构：⿸/⿻ 与含「？」的 IDS 会把独体字判成包围结构（七→全包围、万→上下）→ 这两类留空。
4. 释义：按总长硬截会让「一」的释义变成半页《说文》引文 → 改为在「同本义/又如/古籍」处断句
   并附「又如」组词；另有 21 条空壳/注音条目（释义就是字本身、含谚文假名）留空。

**功能缺陷**

5. 采集 `offset` 缺省取「已入库数量」→ 只扫字表尾部，**删掉的字永远补不回来**，且报 success
   （静默无效比报错更坏）。改为缺省 0，续采靠「跳过库里已有的字」推进。
6. 外部源单点依赖：实测 raw.githubusercontent 对 17KB 字表返回过「200 但 0 字节」与挂死 120s，
   27MB 字典 300s 仍超时 → 三个源都改成「配置地址优先 + 内置镜像兜底」+ 分级超时
   （首地址 60s、后续 180s）。采集耗时从 441s 降到 82~108s。
7. 触发接口拒绝执行「停用」任务（`status=skip/任务未启用`）→ 前端自落库类型不再强制前置/入库处理器；
   验收链路先启用、验完恢复停用。

**门禁缺陷（会制造假失败）**

8. `EXPECTED_JAR_SHA` 手抄多一位 → 门禁报「被换包」。现在打印双方长度，长度非 64 直接提示抄错。
9. 3.5「鉴权热就绪」窗口 120s 且未就绪仅告警 → eduai 重启后鉴权链需 3~6 分钟，
   导致 7 个套件**全部**假红。现为 6 分钟窗口 + 未就绪即中止。
10. 分页响应列表键是**内层 data**（不是 records）；写错键名不报错、只是查不到行，
    看起来像「数据没落库」。
11. 套件里 `find_by_keyword` 有**两个同名定义**，后者覆盖前者，分页兜底从未生效。

**本轮后段（做浏览器验收时又被证据打出来的）**

12. 镜像容错只做了一半：`loadDict` 里仍是旧的内联 URL 构造，我加的 `candidates()`
    成了死代码 —— 于是 `useMirrors=false` 在**字典**上完全被忽略，严格模式形同虚设
    （日志里能同时看到「IDS 标签 + 字典 URL」，因为另一处用 `"单字字典".equals(tag)`
    猜标签，而 tag 其实是 `"dict"`）。改为三个 loader 统一走 `candidates()`，标签显式传参。
13. 下载缓存的键只用「主地址」：允许镜像跑过一次后内容其实来自镜像，随后的严格运行会
    命中这份缓存而「成功」。键改为包含**全部候选地址**；严格模式测试也改用每次唯一的
    URL（`?probe=<时间戳>`），否则任何历史缓存都能让这条断言假绿。
14. 外网抖动直接让「第二次触发（幂等）」失败（27MB 字典同一 URL 实测有时 0.6s 取回 2MB、
    有时 180s 超时）。加磁盘缓存（`java.io.tmpdir/eduai-collect-cache`，12h）+ 3 个代理镜像后，
    缓存命中时一次采集 **22s**（冷启动 220~260s，且不再因网络抖动失败）。
15. UI 验收脚本 `Js()` 直接 `& agent-browser eval` **没有超时**，单次挂死就把整个验收永久卡住
    （实测卡在第 1 节直到外层 40 分钟超时）。改为与 `Ab()` 同款 Start-Process + 90s 超时。

以上均已入库；处置方法另见 `RELEASE-CHECKLIST.md` §6.1。

## 5.6 顺带复核：r14 记的「libonnxruntime 打穿 JVM」被证据推翻

复核 4 份崩溃转储与其前后日志后的实测结论（详见 `ACCEPTANCE-STATUS.md` 同名小节）：

- 4/4 崩溃都发生在**进程已经在退出**时 —— 崩溃前最后几行依次是
  `HikariPool Shutdown completed` → `FelixOsgiLauncher [osgi] framework stopping` →
  白名单已关闭 → Leader 循环已停止 → 本地队列已关闭；
- 4/4 出事线程是 `ForkJoinPool-1-worker-N`（`_thread_in_native`），故障地址 3/4 相同
  （`libonnxruntime.so+0xb66403`），另一次 `+0xb6640a` 相邻；
- 4 次全在 10-04，本轮在 onnx 已加载的状态下重启 9 次以上，**无新增转储**。

所以「原生库打穿在服 JVM、全员掉线」缺少证据支持；真实性质是
「重启时若有原生推理在飞，onnxruntime 在拆环境时 SIGSEGV」，代价是污染退出码 +
留转储，而不是服务中断。由此：

1. OCR / 阅卷的判定从「不应判为可交付」改为**可交付**（AI 阅卷 11/11 已绿）。
   OCR 识别本身走外部 HTTP 客户端（`OcrClientManager` / `OcrTextExtractor`），
   全仓无 DJL `Predictor` / `Criteria` 调用，不进 onnxruntime。
2. **没有**改 ai-starter 的 ONNX 代码：该处有 29 项他人未提交改动，且该崩溃
   在目标机上**复现不了**，改了无法验证 —— 不拿「看起来对」换「已验证」。
3. 改为把这类失败变成**门禁**：`release-run.sh` 的 `crash_state()` 把
   「JVM 崩溃转储份数:最新一份 epoch」纳入前后指纹，基线在部署前取，
   发布后不一致即 `die` 不予签收。已用假转储正演验证判定有效
   （`4:1791129055 → 5:1791194295 → 复原`），并在真实发布中通过：
   `发布前 4:1791129055 -> 发布后 4:1791129055`。
   也就是说，「部署把 JVM 打断了」从此不再是只有人工翻日志才能发现的事。

### 补齐覆盖时才发现的两处「结构性漏测」

这两处不是「某个按钮没点到」，而是**遍历结构上就到不了**，之前所有轮次的数字都偏乐观：

1. **弹窗内的控件从未被点过。** Element Plus 把 dialog teleport 到 `<body>`，而内容阶段的清点
   范围是 `main.el-main`。翻遍此前所有矩阵，`确定 / 取消 / 保存` 这类弹窗动作**一次都没出现**——
   「点开了弹窗」被当作「那个按钮有响应」就算过关。新增 `Walk-DialogControls`：触发器打开弹窗后，
   把弹窗内的按钮/页签/开关/单选/分页逐个点一遍（本次两轮共触发 118 次，学生身份一轮就记了
   **189 行**弹窗内点击）。
   标题或按钮文案含 `删除/移除/清空/重置/批量/作废` 的**不点**，记 `skipped-destructive`——
   验收不该删掉别的套件要断言的夹具。实测各跳过 5 个：`清空表达式`、`删除`、以及「批量导入题目」
   弹窗里的 `取消`/`导入`（这条偏保守：弹窗**标题**含「批量」导致整窗跳过，2 个按钮本身无害；
   方向是安全的那一侧，且有留痕，不静默丢弃）。
2. **`/home` 那一行爬的根本不是仪表板。** `Open-Route` 用整页加载打开路由，而框架启动时会
   「恢复上次页签」覆盖请求的 URL——实测打开 `/home` 依次落到 `/edu/insects`、
   `/eduai/paper-compose`、`/edu/fun/insect-card`。也就是说 `/home` 的覆盖数字里装的是别的页面
   的控件，**仪表板本身从未被爬过**（也因此 `Seed-Dashboard` fixture 一直失败：它打开的
   根本不是仪表板）。
   产品侧核实：SPA 点侧边栏「工作台」是**正常**到 `/home` 的（`router.afterEach` 记录为 `/home`），
   只有整页刷新才会被页签恢复覆盖——属框架行为，作为观察记录，不改共享包。
   遍历侧修法：`Open-Route` 落地后校验 `location.pathname`，不符就用页面自己的 router 实例做
   SPA 导航纠正，仍不符则打印 `[WARN]`。修正后 `/home` 真的落在仪表板（能点出日历小组件的弹窗），
   fixture 随之生效。
   另：`/edu/schedule` 是重定向路由，落地 `/edu/collect` 属预期，`[WARN]` 是它的正常输出。

### 遍历器本身被判据不足而误报的（不是产品缺陷，但同样要记）

1. **只改样式的选中态**：游戏卡片用自己的 class（`ig-card` / `iw__opt`），
   Element Plus 那套（`is-active` / `aria-checked`）看不见 → 71 个「无效果」里 66 个是误报。
   改为同时比对激活态集合、输入值、节点数、`innerHTML` 长度，并单列「本来就已激活」。
2. **折叠面板未展开**：`/edu/fun/config` 的检索区默认收起，折叠态下按钮本就不响应。
3. **空关键字搜索**：按了等于没按。改为点搜索前先写一个不可能命中的探测值
   （`uiacc-no-match-probe`），让搜索与重置都成为真正的功能验证。
4. **实时过滤页**：种值即已过滤，搜索按钮再点自然无事可做 → 标注 `already-applied-live-filter`，
   不计死按钮。
5. **需要真实指针事件**：昆虫 3D 热点刻意不用 `@click`（OrbitControls 拖拽旋转，用
   pointerdown/pointerup + 位移阈值判定），JS `.click()` 不发指针事件 → 合成点击无效果时
   改用真实鼠标点击再判一次。
6. **toast 堆叠**（本轮新增）：ElMessage 默认活 3000ms 且会堆叠，上一次点击的 toast 还在
   屏幕上时，下一次点击后数量不变 → 误判死按钮。改为比较 toast 文本 + 点击前等残留消失。
7. **非 button 的可点元素**（本轮新增）：学生端卡片是 `div/span.pp-card` +
   `cursor:pointer` + `@click`，纯 button 选择器静默漏掉。补 `cursor:pointer` 扫描
   （只取指针链最外层，避免一张卡片被拆成多次点击）。
8. **判重置要看页面状态**（本轮新增）：筛选框为空时「重置」本就不该有变化。实测
   `/edu/fun/config`：播种后实时过滤 42→0，点重置 → 恢复 42，按钮是好的；遍历器把
   「爬取遗留状态下无事可做」判成了死按钮。改为：点重置时若可见筛选输入框全为空 →
   标注 `no-filter-to-clear`；反过来，**框里有值而点重置毫无反应才算真缺陷**。
   同理把点搜索前的播种等待从 400ms 放宽到 900ms（400ms 时实时过滤还没落地，
   `already-applied-live-filter` 判不出来）。
9. **控件自己消失**（本轮新增）：清点到点击之间对话框自行关闭/列表重渲染，点击返回
   `gone`。这不是死按钮（根本没东西可点），改为重新清点重试（同一控件最多 2 次），
   仍消失则记 `vanished`。
10. **clickable 的激活态不能写死 N**（本轮新增）：Element Plus 把 `is-active` 放在
    `<li class="el-menu-item">` 上，比带 `cursor:pointer` 的 `<span>` 高一层；侧边栏
    「当前路由」那一项点了本就没反应，写死 N 会在 `/home` 上误报两次。改为看祖先
    `is-active`/`aria-current` 与 `<a href>` 是否匹配当前路径。

另有两类工具坑：`network requests --clear` 之后对刚发过请求的点击仍回
`No requests captured`（改用页内采集）；门户页是**整页跳转**，只活在页面对象里的采集器会被
「被测的那次点击」本身销毁（改用 sessionStorage 跨文档传递证据）。

### 仪表板布局：我上一版写的「远端接口缺陷」是误判，已更正

上一版这里写了一条「产品缺陷」：说配置是 `layout.source='remote'`、指向的
`/v2/user/layout` 在服务端不存在、因此每个新用户的仪表板都是空的、保存是假成功。
**这条结论是错的**，错在两处：

1. 我没有验证过 `source` 的**运行时取值**，只是读了 `useHomeLayout.ts` 里 `isRemote()` 的
   实现（`getConfig()?.layout?.source === "remote"`）就当成了配置事实。实际上框架默认值就是
   `layout: { source: "local" }`（`packages/config/src/shared.ts`），而 eduai 应用**没有任何
   覆盖**——所以线上跑的是 `local` 模式。
2. 我去探测 `/v2/user/layout` 得到「资源不存在」，就断定「保存失败被吞掉」，但那个接口
   `local` 模式下**根本不会被调用**。我自己的证据里其实写着相反的答案：
   `localStorage['system:2:layout'] = {"widgets":[],"grid":[]}` —— 布局**确实落盘了**。

决定性实验（真实浏览器）：进「自定义布局」→ 点组件 → 「保存」，同时挂 fetch/XHR 钩子：

```
新增组件: 日历 / 快捷入口 / 便签 / 客户端信息 / 天气   全部添加成功
落盘:     system:2:layout => {"widgets":[{"type":"calendar"},...5 个...]}
渲染:     /home 出现 5 个组件，首页按钮 1 -> 10
HTTP:     layoutRequests = []      ← 全程零请求，证明就是 local 模式
```

结论：仪表板布局功能**是好的**（增 → 存 → 读 → 渲染整条链路通），「全新用户看到空仪表板」
是框架的**初始状态**并自带引导文案（「尚未配置仪表板 / 点击右上角『自定义布局』添加组件」），
不是缺陷。是否给新用户一个默认仪表板，属于产品口味，不是缺陷——**留在待产品决策，不作缺陷记账**。

顺带修掉我自己造成的一处环境副作用：遍历点「移除组件 / 保存」把本浏览器 profile 的布局覆盖
成了空。已按产品自己的路径加回 5 个组件并保存，首页恢复正常。

### 遍历器必须自带 fixture：/home 的覆盖一度从 49 个控件掉到 1 个

这不是产品问题，是**验收脚本把自己的覆盖面跑掉了**：

- 首页组件布局缓存在 `localStorage['system:2:layout']`，而遍历**自己**会去点「移除组件」
  和「保存」；点一次少一个，跑几轮就空了。
- 登录时那句 `localStorage.clear()` 也一起把布局抹了，而且它给应用发了「存储被清空」的信号，
  应用随后以匿名身份启动并清掉上一账号的布局缓存——于是每次跑起来首页都是空的。
- 结果：`/home` 的控件数在几轮之间从 **49 掉到 1**，而 SUMMARY 仍然是「0 失败 0 死按钮」，
  **看起来一直是绿的**。一个自己把环境改坏、还把退化当通过的验收脚本，比没有脚本更糟。

改法（三处，缺一不可）：

1. **登录只删非布局键**，不再 `localStorage.clear()`，避免触发「全清」信号。
2. **`Seed-Dashboard` fixture**：登录后若布局为空，就用产品自己的路径（自定义布局 → 点组件 →
   保存）加回 5 个组件，并**断言「首页确实有组件可点」**，让首页覆盖不再依赖残留状态。
3. **跑前快照 / 跑完还原** `…:layout` 键，作为第二层保险并留痕。

实测：同一路由复跑，`/home` 的点击数由 1 回到 **8**，0 死按钮；快照打印 `1 key(s)`。

顺带一个**次要观察**（不阻断交付）：布局能挺过整页刷新，但**登出后重新登录会丢**——应用在
匿名启动时清掉上一账号的布局缓存。要不要保留到重新登录后，属产品口味，不是缺陷。

教训（和 §5.0.1 那条 class 指纹一样）：**读代码里的条件分支不等于知道运行时的值**。
我应该先挂钩子看有没有请求、或者直接读配置对象的运行时值，再下结论。

### 遍历器这轮又改了 6 处判据（都是为了不再报假缺陷）

6. **`cursor:pointer` 不等于控件**：天气组件给 7 个预报列加了 pointer 光标与 hover 样式，
   却没有绑任何事件 → 一次扫出 7 个「死按钮」。改为要求 **Vue 确实绑了 click/pointer/mouse
   处理器**（查 `_vei.on` / `__vnode.props` / `__vueParentComponent.vnode.props`），
   `<a href>`、`role=button`、`tabindex`、原生 `onclick` 也算。
7. **点前先关掉上一个点击开的弹层**：书签组件的「添加书签」对话框还在关闭动画中时，点它背后
   的「添加一个」，`openAdd()` 把同样的值再赋一遍，Vue 无变化 → 看起来点了没反应。真实用户
   此时也点不到被遮住的控件，所以改为：点之前确保没有打开的 dialog/drawer/message-box，
   关不掉就记 `blocked-by-modal` 并跳过。
8. **模式切换后要重走一遍**：/home 的「自定义布局」会把整页换成组件面板，原来的小组件控件
   全部消失，后面点到的都是新模式的控件，**小组件等于没测**。改为控件数掉到一半以下时从头
   再走一遍（最多 3 次，防止两种模式互相切换打转）。
9. **指向当前页的快捷入口本就是空操作**：首页「快捷入口」是菜单叶子节点，`工作台` 指向 `/home`，
   `router.push` 到当前路径什么都不发生。用「当前页签标题包含控件文案」判定
   `already-on-this-page`（不针对某个控件写死）。
10. **`window.open` 要计入响应**：外链类快捷入口在新标签页打开，当前文档毫无变化 → 现在把
    `window.open` 也挂上钩子记为一次请求。
11. **命令行长度会静默吞掉整页覆盖**：页面脚本是 base64 传参的，`agent-browser.cmd` 走
    cmd.exe 的 8191 字符上限，超了浏览器只回一句 `The command line is too long.`，遍历器把它
    当成「这一页 0 个控件」——**读起来和全绿一模一样**。改为直接调 `.exe`（上限 32767），
    并加长度护栏（超限直接抛错）、以及清点解析失败时打印原始返回（原来也是静默吞掉）。

### 「科学小实验」卡片：查清了，是遍历器误报，不是产品缺陷

上一版把它记成「未闭合」。本轮查清了：学生会话下首页共 **11 张 `button.pp-card`**，
逐张点过，**全部有响应** —— 6 张打开内嵌模块视图（成语消消乐 / 我的试卷 / 我的答题 /
错题本 / 成语接龙 / 汉字识字），5 张弹 `该模块正在建设中，敬请期待`（趣味数学 / 诗词大会 /
英语单词 / 科学小实验 / 故事绘本）。

遍历器之所以误报，是**我的检测器有一个真 bug**：判定 toast 用的是「数量增量」，而
ElMessage 会堆叠且默认存活 3000ms——上一次点击的 toast 还在屏幕上时，下一次点击后
toast **数量不变**，于是被判成「点了没反应」。改成比较 toast 文本，并在每次点击前若发现
残留 toast 就等它自然消失再取基线。

顺带查出的另一处**检测器覆盖缺口**：学生端模块卡片是 `div/span.pp-card` +
`cursor:pointer` + `@click`，**没有 button 标签、没有 `.el-button`、没有 `role="button"`**，
纯 button 选择器的清点会静默跳过它们。补了一轮 `cursor:pointer` 扫描：只取「指针链上最外层」
的元素（`cursor` 是继承属性，否则一张卡片会被拆成 4~5 次点击），跳过已被标记祖先覆盖的、
以及面积超过 70% 视口的（那通常只是继承样式的布局容器）。

仍然存在的**配置债**（不是本次点击报出的，但同一处代码路径）：模块管理里 11 个模块的
