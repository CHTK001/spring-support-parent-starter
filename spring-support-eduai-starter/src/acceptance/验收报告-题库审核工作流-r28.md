## 三、本轮发现并修复的两个真实缺陷

### 缺陷 1：非选择题建题 500（生产日志实锤）
```
Caused by: java.sql.SQLIntegrityConstraintViolationException:
  CONSTRAINT `edu_question.question_options` failed for `eduai`.`edu_question`
```
- 根因：`edu_question.question_options` 有 `CHECK (json_valid(question_options))`，
  而 **MariaDB 的 `json_valid('')` 返回 0（不是 NULL）** —— 空串被约束拒绝。
  判断题/填空题/简答题/作文本就没有选项，前端会传 `""`，必然插不进去。
- 修复：`unwrapJsonText` 对空白入参归一为 `null`（`json_valid(NULL)` → NULL → 约束通过）。
- 影响面：已核全库 9 个 `json_valid` CHECK 约束，本模块只 `edu_question.question_options` 一处；
  其余 8 个属 sys_ai / 试卷 / 答题卡 / 阅卷表，不在本次改动路径上。
- 验收：判断题新建 save 由 **500 → 200**（返回 id 56012）。

### 缺陷 2：保存并审核的审核次数漏计
- 表现：状态是「已通过」但没有 `×N`，与"每次审核 +1"口径对不上。
- 修复：`auditOnSave` 分支审核次数从 **1** 起算（这次保存本身即一次审核动作）。
- 验收：`ZZon-5603753` → `已通过 ×1`。

## 四、验收方法与判定口径（重要）

### 必须走浏览器，不能裸 curl
POST 请求体经前端 wasm **AES 加密**（`x-ck` 头 + 密文 body），裸 curl 的明文 JSON
一律被判 `D0409S0003 必填字段不能为空` / `C0400S0002 请求数据格式错误`。
这是**既有机制，不是审核改动引入的**。所有结论均来自真实页面操作 + 生产库核对。

### 判定口径：按审核状态列**文字**，不按 class
`is-green` / `is-red` 同时被 `auditClass`（审核）和 `diffClass`（难度）复用，
按 class 计数会把难度 pill 误当审核状态。正确做法是读状态列文本（待审核/已通过/驳回）。

### 组卷入口的三个坑（均非缺陷）
1. 「题库」「组卷」按钮**只在草稿态**试卷行渲染（`paperStatusCode === 0`）
2. 操作列是 `el-table fixed="right"`，宽视口下整列在视口外，`is_visible=false`
3. 组卷页入口是 `ReButton tip="继续添加题目"` —— tip 只进 tooltip、**不进 DOM 文本**，
   按文本/按钮文字都找不到，须按 `aria-label`
→ 最终直进路由 `/eduai/paper-compose?paperId=9036`（库中草稿试卷）

### 早前几版误报的 4 个"失败"（均为断言写错，非产品缺陷）
- 「采集页含文案」→ 开关在编辑弹窗内，页面本身不渲染（弹窗断言已 PASS）
- 「审核次数 count=0」→ 库里当时 169 题 `audit_count` 全为 0，前端 `v-if count>0` 不渲染是对的
- 「筛选下拉 >= 6」→ 实际 5 个（keyword 是 input 不是 select）
- 「待审过滤后条数未收窄」→ 待审 ≥ pageSize(20) 时前后都是满页，条数不变才对；
  真正要证的是"状态列只剩待审"，该条 PASS
