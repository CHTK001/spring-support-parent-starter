## 八、§23 工号可直接登录（r48，2026-10-15）

需求：**工号也需要可以登录**（不再强制「先用系统账号登录、再在老师端绑定工号」）。

### 23.1 现象与判据

`POST /v2/user/login`，body 带 `accountType=teacher` + 工号 + 口令 → **500 `S0512C0000 系统处理异常`**。反例（口令错误 / 工号不存在）返回**同一个** 500，说明请求在「凭据校验之前」就失败了。

### 23.2 根因链（逐层，全部有源码或运行时实证）

1. `SysLoginServiceImpl#login` 把 `LoginHandler` 的扩展名组合成
   `Joiner.on("-").skipNulls().join(loginData.getLoginType(), loginData.getAccountType())`。
   请求里 `loginType` 为空、`accountType=teacher` → 组合出的查找名是 **`teacher`**。
2. 框架只自带 `DefaultLoginHandler`（`@Spi("WEB")` + `@SpiDefault`）与 `WeixinMiniLoginHandler`（`@Spi("WECHAT")`），**没有名为 `teacher` 的处理器** → `getNewExtension("teacher")` 返回 `null` → 调用方在 `null#login(...)` 上抛空指针 → 对外 500。
   运行时原文：`[ServiceProvider] 扩展实例化失败: name=teacher args=0`。
3. 管理员登录之所以正常，是因为前端不传 `accountType` → 组合出的名字为空 → 走 `getEmpty 分支的 getDefaultImpl()`，命中 `@SpiDefault` 的 `DefaultLoginHandler`。**同一个接口，空名字能兜底，非空名字不能** —— 这是掩盖问题的关键差异。
4. 我此前只注册了 `CredentialProvider`（oauth「按账号来源解析」的扩展点），**漏了登录分发口的 `LoginHandler`**：凭据实现再好，也到不了「校验口令」那一步。

### 23.3 补 `LoginHandler` 过程中实测踩到的三个框架级陷阱（都与「SPI 大小写/实例化」有关）

- **重载陷阱**：`ServiceProvider` 有 `register(String, Object)` 与 `register(String, Class<T>)` 两个重载。因泛型不变性，`register("TEACHER", TeacherLoginHandler.class)` 会落到 `(String, Object)`，于是 `setImplClass(ref.getClass())` 拿到的是 **`java.lang.Class`**。实测报错：
  `原因=无参兜底实例化失败（该类无可用无参构造器）… 实例化构造调用失败: java.lang.Class`。
  必须显式写 `Class<LoginHandler> impl = (Class<LoginHandler>) (Class<?>) TeacherLoginHandler.class;`（已用 `javap -c` 核对字节码确实调用了 `register:(Ljava/lang/String;Ljava/lang/Class;)V`）。
- **实例化陷阱**：`getNewExtension(...)`（登录口用的 API）**不返回** `register(name, obj)` 预置的那个实例，而是按 `implClass` 的构造器**反射新建**（`ServiceDefinition#newInstance` 只看 `implClass`）。因此处理器必须**无参可构造**，依赖不能在构造器里注入。
- **SOFT 缓存陷阱（本次最隐蔽）**：`ServiceProvider.CACHE` 是 `ConcurrentReferenceHashMap`，其 `DEFAULT_REFERENCE_TYPE = ReferenceType.SOFT`。本机 JVM 常驻 2~3G 且 `MemoryMax=4G`，内存吃紧时缓存里的 **Value（ServiceProvider 实例）会被 GC 回收**；之后 `ServiceProvider.of(...)` 会**重新构造**实例，而 `register(...)` 写在旧实例上的注册随之丢失 → 出现「启动日志显示注册成功、请求时却查不到」。两次行为不同的实测（同一注册路径，一次报 `java.lang.Class`、一次报 `原因=null`，后者即 `implClass == null` 的 `DEFAULT_DEFINITION`）指向同一结论。
- **大小写**：`register`/`getDefinitions` 两侧都 `toUpperCase()`，`ServiceDefinitionFinder` 的名字匹配用 `equalsIgnoreCase`，且 `register(name,obj)` **不调 `setName()`**（所以按名匹配那条循环对显式注册恒不命中，实际靠大写键命中）。结论：**注册名写大写的 `TEACHER`，请求组合出的 `teacher` 同样命中**。

### 23.4 最终修复（三处，均在 eduai 模块内）

1. 新增 `TeacherLoginHandler implements LoginHandler`：`@Spi("TEACHER")`、**无参可构造**；只做两次翻译（`LoginData`→`CredentialRequest`、`LoginAuthResult`→`LoginResult`），真实校验全部委托给既有且已验过的 `TeacherCredentialProvider`（**口径只有一份**，不与静态协议链路分叉）；异常兜底成业务失败，不再吐 500 堆栈。
2. 新增 `src/main/resources/META-INF/extensions/com.chua.starter.system.handler.LoginHandler`，内容 `TEACHER=com.chua.starter.eduai.support.credential.TeacherLoginHandler`。框架的 `CustomServiceResolver` 在 **provider 构造期**读该目录 → provider 被回收重建后会**重新发现**该实现，注册不丢。这是本次能稳定通过的关键。
3. 凭据实现**启动期静态绑定**（`TeacherLoginHandler.bind(provider)`），查 SPI 注册表只作兜底 —— 不再依赖那个会被 SOFT 回收的缓存。

### 23.6 边界与顺带查实的问题（如实）

- **令牌身份口径不变**：教师令牌的 `userId` 取「已绑定的登录账号」（教师 1 绑 `'1'`），未绑定时取工号并顺手写入绑定列 —— 保证历史数据归属连续；角色只给 `TEACHER`（`userInfo.roles` 实测即 `["TEACHER"]`，不含 ADMIN/SUPER_ADMIN）。

## 十、§25 SPI `getNewExtension` 未命中时回落默认实现（框架级，r49）

### 25.1 依据：两个 API 语义不一致

| API | 未命中（非空名字未注册）时 |
|---|---|
| `getExtension(name)` | 回落 `getDefaultImpl()`（`Optional...orElse(getDefaultImpl())`） |
| `getNewExtension(name, args)` | 返回 **null**（`Optional...orElse(null)`），且只有**名字为空**时才走 `getDefaultImpl(args)` |

未注册的名字会让 `getServiceDefinition` 返回空的 `DEFAULT_DEFINITION`（`implClass == null`），`ServiceDefinition#newInstance` 直接 `return null`，于是 `getNewExtension` 返回 null。调用方（如 `SysLoginServiceImpl#login`）通常立刻在返回值上调方法 → NPE → 对外 500，而**扩展名**这个最有用的信息在调用栈里消失。

改动前基线实测（同机同接口）：`accountType=nosuchtype` → `{"code":"S0512C0000","msg":"系统处理异常，请稍后重试"}`。

### 25.2 修改

`utils-support-parent-starter/.../spi/DefaultServiceProvider.java#getNewExtension(String, Object...)`：实例化仍为 null 时，先回落 `getDefaultImpl(args)`（即 `@SpiDefault` 的实现）；**仍取不到**才按原样记 WARN 并返回 null。这样：

- 有默认实现的 SPI：未命中 → 默认实现（与 `getExtension` 对齐）；
- 没有默认实现的 SPI：行为与改动前一致（仍是 null + WARN）。

### 25.3 影响面与验证

- 该模块被所有模块共享，改的是**公共**语义。副作用是「未命中不再返回 null 而是默认实现」——这正是 `@SpiDefault` 的意图，也让 `getNewExtension` 与 `getExtension` 一致。
- 验证：两套登录脚本里的「未知 `accountType` 不是 500」断言（改动前实测为 500，改动后应为业务响应）；并复跑教师/学生全量断言确认无回归。

## 十四、§29 统一登录页（工号 / 学号）的 UI 级登录验收 + 两起环境事件（r50）

### 29.1 先把「统一登录页」认对（此前一度测错页面）

- 真正的**统一登录页**是应用自带的 `/edu/student-login`（趣味学习登录页）：账号框提示「**请输入学号 / 工号 / 手机号**」，提交时按账号形状分流——
  纯数字(6~20 位) → `studentLogin`（`accountType=student`）；其它 → 先 `teacherLogin`（`accountType=teacher`），教师凭据不认再回落系统账号。
- 框架自带的 `/login`（后台管理系统登录页）只提交 `{username,password,codeKey,securityCode}`，**不带 `accountType`**，因此它服务的是 `sys_user` 账号；用「工号」在它上面测会得到 `C0400S0004`，那是**口径错误**而非功能缺陷。已按页面职责区分开。

### 29.2 工具与口径

`src/acceptance/ui-unified-login-e2e.cjs`（Playwright，真机 headless Chromium）：真实填表 + 真实点击「登录」，同时抓**请求体原文**与**服务端响应原文**；身份证据取自登录响应的 `data.userInfo`（本部署令牌是**不透明串**而非 JWT，无法解载荷；口径与 `check-teacher-login.sh` 一致）。
